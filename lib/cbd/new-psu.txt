NEW PSU IMPLEMENTATION
======================

* should be compatible with previous implementation

* support both generic and form/sense-specific matching

* generic sig derived from @parts and may include sense but usually doesn't

* generic sig has ** for psu-form and gw-only or gw-sense dependent on @parts spec

* form/sense-specific sigs derived from @form belonging to @psu entries

* specific sigs have psu-form derived from @form and gw-only or gw-sense dependent on @parts spec

* 3 types of PSUs depending on origin:
  PSU_PART = from @parts
  PSU_FORM = from @form in a glossary
  PSU_INST = from corpus

* 2 overall parts to a PSU:

  PSU_KEY::PSU_PARTS

  PSU_KEY => '{' CODE PARTS += PSU_CGP '}'
  CODE => '-' | '+' | '=' where '-' == PSU_PART; '+' == PSU_FORM; '=' == PSU_INST
  PARTS => CGP CGP+
  PSU_PARTS => SIG '++' SIG ('++' SIG)*

* PSU_PARTS can be empty if all elements in @parts are simple CGP

* if PSU_PARTS is non-empty it must always have a PART for each CGP in PARTS

* SIG can be sparse:

  ** For PSU_PART, SIG has any elements given in the @parts spec,
     allowable constraints are on SENSE, EPOS, BASE, MORPH, NORM, STEM

  ** For PSU_FORM, SIG has any elements given in the @parts spec, plus
     the FORM.  Each FORM is used with the CGP of each PARTS CGP to
     create a FCGP, i.e., a CGP with the form prepended separated by
     '=' in the usual way.  Each list of PARTS is then searched for a
     matching FCGP--this is how multiple @parts with different
     ordering of constituents works.  For a @form to match one of the
     @parts, all of the elements of the @form must match one of the
     @parts specs in order and with no omissions or additions.  Once
     the list of FCGPs is determined, the LANG of each FCGP is also
     supplied for each PSU_PARTS SIG. Thus, each SIG of PSU_FORM
     PSU_PARTS contains the members given in the @parts, plus FORM and
     LANG.

  ** For PSU_INST, SIG is the entire instance signature as pointed to
     in the linkset entry for the PSU match.

* How PSU SENSE Works

PSUs can have multiple senses in the glossary but because all matching
is done on the PSU_KEY, which has no SENSE component, there is no way
of selecting a PSU SENSE automatically; PSU SENSEs must be given
manually in the corpus lemmatization using the += notation on the
lemmatization of the PSU head.


XXX

====

* @entry with a CF that has spaces is a PSU

* @entry* is an MWE (formerly a 'usage')

* in @parts the argument line is an ngram that can be used to match the PSU via the ngrammer

* glosigx/gx validates @parts only via the CGSPE (most elements of most @parts will be CGP)

* gx/glosigx outputs @parts lines to either psus-LANG.ngm or mwes-LANG.ngm

* the output format is NGRAM += PSU_CGSPE

* the lemmer/ngrammer selects candidate PSU/MWE matches using the
  NGRAM; manual disambiguation of SENSE/EPOS is available via += in
  the GW part of the head noun of a PSU

* @form is optional for PSU/MWE; if given, signatures are written to
  psus-LANG.sig which can be used for secondary disambiguation and
  glossary validation

* PSU/MWE lemmatization occurs in the following sequence

  1) lemmatization of single constituents
  2) selection of candidate PSU/MWE including use of +=SENSE on PSU head in corpus
  3) disambiguation of PSU/MWE via .sig if available
  4) disambiguation of PSU/MWE via SENSE rank if applicable
  5) output PSU/MWE linkset
